# PostgreSQL 운영 가이드

ProcureLedger 는 SQLite(기본, 파일 하나)와 PostgreSQL 15 이상을 지원한다. 데모·소규모는 SQLite 로 충분하고, 동시 사용자가 늘거나 백업·복구·감사 요구가 커지면 PostgreSQL 을 쓴다. 이 문서는 PostgreSQL 로 운영할 때의 권장 구성과 SQLite 에서 옮기는 절차다. 명세는 해당 기능 명세.

## 1. 지원 범위

- 지원 버전: PostgreSQL 15 이상(개발 검증은 16). 확장은 필요 없다.
- 서버(`bin/server`)는 **한 대**만 띄운다(같은 데이터베이스에 서버가 둘 뜨지 않는다). `erp-mcp` 는 여럿이어도 된다.
- 웹 화면이나 API 로 데이터베이스를 바꿀 수 없다. 데이터베이스 선택은 서버를 띄우는 운영자의 환경 변수다.

## 2. 데이터베이스와 역할 만들기

```sql
CREATE ROLE pl LOGIN PASSWORD '<비밀번호>';          -- 슈퍼유저가 아니다
CREATE DATABASE procure OWNER pl ENCODING 'UTF8' LC_COLLATE 'C' LC_CTYPE 'C' TEMPLATE template0;
```

- 정렬 규칙은 `C` 를 권장한다(SQLite 와 같은 바이트 순서 정렬이라 화면의 정렬·검색 결과가 달라지지 않는다).
- 앱 역할은 데이터베이스 **소유자**여야 한다(마이그레이션과 이관이 표 소유자 권한을 쓴다). 슈퍼유저는 필요 없고 주지 않는다.
- 비밀번호는 연결 문자열에 쓰므로 비밀 저장소(환경 변수·시크릿)에만 둔다. 로그와 오류에는 가려진 값만 나온다.

## 3. 연결

| 환경 변수 | 설명 |
|---|---|
| `PL_DB_URL` | `postgres://pl:<비밀번호>@<호스트>:5432/procure?sslmode=verify-full`. 지정하면 `PL_DB_PATH` 는 무시된다 |
| `PL_DB_MAX_CONNS` | 연결 풀 상한(기본 10, 2~100). 서버 `max_connections` 는 앱 + `erp-mcp` + 관리 여유보다 크게 |
| `PL_DB_ALLOW_INSECURE` | `1` 이면 **루프백**에서만 TLS 없는 연결을 허용한다(로컬 개발). 원격은 `sslmode=require` 이상이어야 기동한다 |

- 운영은 `sslmode=verify-full` 과 서버 인증서 검증을 권장한다.
- 같은 데이터베이스를 `erp-mcp` 도 같은 `PL_DB_URL` 로 연다.
- 서버와 데이터베이스 서버의 시계를 맞춘다(NTP). 앱은 시각을 UTC 문자열로 저장한다.

## 4. 처음 기동

빈 데이터베이스에 `PL_DB_URL` 만 주고 서버를 띄우면 PG 용 마이그레이션이 자동 적용된다(적용은 파일 하나당 한 트랜잭션이고, 동시에 여러 프로세스가 떠도 advisory lock 으로 하나만 적용한다). 이후 설치 마법사·개발 시드는 SQLite 와 같다.

## 5. SQLite 에서 이관하기

기존 SQLite 데이터를 빈 PostgreSQL 로 한 번 옮기는 도구가 있다(`erp-admin db-migrate`, 서버는 멈춰 둔다).

```
erp-admin db-migrate --from /data/erp.db --to 'postgres://pl:<비밀번호>@db:5432/procure?sslmode=verify-full' [--dry-run]
```

비밀번호가 명령줄(셸 기록·프로세스 목록)에 남지 않게 하려면 `--to` 대신 환경 변수 `PL_MIGRATE_TO` 에 연결 문자열을 넣는다. 로컬 개발에서 TLS 없는 루프백 연결을 쓸 때만 `--allow-insecure` 를 더한다. `./bin/server db-migrate …` 로도 같은 명령이 실행된다(호환 별칭). 이관을 마치면 대상 감사 체인 끝에 `system.db_migrated`(경로 cli, 원본 SHA-256·표별 행 수 요약, 비밀 값 없음)가 한 건 붙고 체인을 다시 검증한다.

순서와 동작:

1. **사전 조건**: 원본 SQLite 파일을 **읽기 전용**으로 연다(원본은 어떤 경우에도 수정하지 않는다). 원본의 마이그레이션 최종 번호가 PG 기준과 같아야 한다(다르면 "원본을 먼저 최신으로 올리세요"). 대상은 비어 있어야 한다(핵심 데이터 표에 행이 있으면 거부, 덮어쓰지 않는다). 원본이 2GB 를 넘으면 한 트랜잭션으로 옮기지 않는다.
2. **복사**: 대상에서 **한 트랜잭션**으로 진행한다. 표마다 보호 트리거를 `ALTER TABLE … DISABLE TRIGGER USER` 로 그 트랜잭션 안에서만 끄고, 적재 뒤 다시 켠다(표 소유자 권한만 필요). 트리거를 영구히 우회하는 설정은 없다. 표는 외래 키 순서로 옮기고, 순환·자기 참조는 먼저 비워 두었다가 나중에 채운다. 번호·시각·해시는 원본 글자 그대로 넣는다. 로그인 세션·호출 제한 창·일회용 링크 같은 임시 표는 옮기지 않는다(이관 뒤 다시 로그인한다).
3. **검증(모두 통과해야 커밋)**: 표별 행 수와 내용 체크섬, 감사 해시 체인 검증과 체인 끝(번호·해시)이 원본과 같음, 전표 차대변 합 0, 재고 합계와 원장 합 일치, 음수 재고 없음. 번호 시퀀스는 최대 번호로 맞춘다. 하나라도 어긋나면 모두 되돌린다.
4. **판정표**: 표별 행 수·체크섬 일치와 체인 결과를 한국어 표로 출력하고, 통과하면 종료 코드 0 이다.
5. `--dry-run` 은 모든 검사를 하고 마지막에 되돌린다(운영 전 리허설). 스키마는 대상에 적용된 채 남지만 데이터는 남지 않는다.

이관 뒤:

- `PL_DB_URL` 을 설정하고 `PL_DB_PATH` 는 비워서 서버를 띄운다.
- **봉인 키는 같은 값**이어야 한다: `PL_ACCOUNT_SECRET_KEY` 가 다르면 이관된 계좌번호를 풀 수 없다(키는 백업·데이터베이스와 따로 보관한다).
- **감사 앵커 파일도 함께 옮긴다**: 앵커를 쓰고 있었다면(`PL_AUDIT_ANCHOR_KEY` 설정) 이관된 DB 에는 앵커를 찍은 기록이 그대로 들어 있지만, 서명한 줄은 DB 밖 파일에만 있다. 새 서버가 빈 파일이나 다른 경로를 가리키면 감사 검증이 `anchor_lost`(DB 에는 앵커 기록이 있는데 파일에 그 줄이 없음)로 나온다. 절차: ① 서버를 멈추고 이관을 마친 뒤 ② 원본 서버의 앵커 파일(`PL_AUDIT_ANCHOR_PATH`)을 **복사본**으로 새 서버 쪽 볼륨에 둔다(원본 파일은 롤백을 위해 남긴다) ③ 새 서버의 `PL_AUDIT_ANCHOR_PATH` 를 그 복사본으로, `PL_AUDIT_ANCHOR_KEY` 를 원본과 **같은 값**으로 설정한다 ④ 서버를 띄운 뒤 관리자 화면 감사 로그의 검증을 실행해 앵커 대조가 정상인지 본다. 앵커를 쓰지 않던 환경은 해당 없다.
- **롤백**: 원본 SQLite 파일은 그대로 남아 있다. 문제가 생기면 `PL_DB_URL` 을 비우고 `PL_DB_PATH` 로 되돌아가면 된다(이관 이후 PG 에서 쓴 데이터는 되돌아가지 않는다).
- 이관 중 중단되거나 검증에 실패하면 대상 데이터는 되돌려진다. 대상에는 스키마(시드 포함)만 남아 있으므로 같은 대상으로 다시 시도할 수 있다.

## 6. 백업과 복구

- 논리 백업: `pg_dump -Fc procure > procure-$(date +%F).dump` 를 일 1회. 필요하면 WAL 보관(PITR)을 추가한다.
- 복구: 빈 데이터베이스를 만들고 `pg_restore -d procure procure-….dump`. 복구한 뒤 서버를 띄우고 **감사 무결성 점검**(관리자 화면)으로 해시 체인이 이어지는지 확인한다. 복구 연습을 정기적으로 한다.
- 백업 파일은 계좌번호가 봉인돼 있어도 개인정보를 담고 있으므로 암호화하고 접근을 통제한다.

## 7. 보안 권장

- DB 역할 최소 권한: 앱 역할은 이 데이터베이스의 소유자일 뿐 슈퍼유저가 아니다. 다른 앱과 데이터베이스를 공유하지 않는다.
- `pg_hba.conf` 에서 앱·`erp-mcp` 호스트만 허용하고 TLS 를 강제한다(`hostssl`).
- 감사 로그는 추가 전용이다. 데이터베이스 관리자가 직접 고치면 체인 검증이 잡아내지만, 막지는 못하므로 DB 접근 권한 자체를 최소화한다.

## 8. 동시성과 장애 대응

- 번호 발급(문서·전표·지급·재고)은 같은 종류·연도의 행 잠금으로 줄을 선다. 동시에 많이 몰리면 서로 기다릴 뿐 번호가 겹치거나 비지 않는다.
- 월 마감 중에는 그 달에 쓰는 전표·입출고·실사가 마감이 끝날 때까지 기다린 뒤 마감 결과(닫힘)를 보고 거절된다. 입고는 발주 줄을 잠근 뒤 잔량을 검사한다.
- "잠금 대기 시간 초과"(`lock_timeout`, 기본 10초) 오류가 반복되면 오래 열린 트랜잭션이 있는지 `pg_stat_activity` 로 본다. 교착은 PG 가 한쪽을 되돌리며 사용자는 다시 시도하면 된다.
- `work_mem` 은 기본값으로 충분하고, 자동 `VACUUM` 을 켜 둔다.

## 9. 개발자: PostgreSQL 로 시험 돌리기

`make verify`(Docker 없이 SQLite)와 별도로 `make verify-pg` 가 임시 PostgreSQL 클러스터를 띄워 같은 시험을 PG 로 돌린다(`PL_VERIFY_PG_PKGS` 로 패키지 한정, `PL_VERIFY_PG_DETAIL=1` 이면 실패 첫 줄 출력). 시험이 데이터베이스를 얻는 곳은 `internal/dbtest` 한 곳이고, SQLite 전용 시험은 사유와 함께 건너뛰며 건너뛴 목록은 상한이 있다.
