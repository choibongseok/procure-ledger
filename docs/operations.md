# 운영 매뉴얼

서버를 설치하고 운영하는 사람을 위한 문서다. 코드가 아니라 서버 호스트에서 하는 일(설치·업그레이드·백업·복구·키 교체·장애 대응)을 순서대로 적는다.
명세 정본은 해당 기능 명세(백업·복구·키 교체), 해당 기능 명세(PostgreSQL), 배포 산출물은 [docs/deploy-checklist.md](deploy-checklist.md) 다.

> **원칙**: 백업·복구·키 교체는 **서버 호스트에서 `erp-admin` 으로만** 한다. 웹 화면에서는 실행할 수 없다(웹 세션이 탈취돼도 DB 를 덮어쓰지 못하게). 모든 명령은 서버와 같은 환경변수(`PL_DB_PATH` 또는 `PL_DB_URL` 등)로 같은 DB 를 연다. 출력에는 비밀값이 나오지 않는다.

## 1. 개요와 구성도

| 구성요소 | 설명 |
|---|---|
| 서버(`bin/server`) | 웹 화면·API·MCP 엔드포인트. 프론트를 임베드한 단일 바이너리(cgo 없음) |
| `erp-mcp` | 표준입출력 MCP 서버. 서버와 같은 DB 를 연다 |
| `erp-admin` | 운영 명령(백업·복구·키 교체·권한 재계산·잠금 해제). 서버 호스트에서만 실행 |
| DB | 기본 SQLite 파일(`PL_DB_PATH`, 기본 `data/erp.db`, WAL 모드). `PL_DB_URL` 이 `postgres://` 이면 PostgreSQL |
| 첨부·로고·직인 | DB 안(BLOB). 별도 파일 디렉터리가 없다: DB 백업이 곧 첨부 백업이다 |
| 감사 앵커 파일 | `PL_AUDIT_ANCHOR_PATH`. 감사 로그의 마지막 기록 삭제·재계산을 잡는 외부 확인 장치. **DB 와 다른 디스크(볼륨)에 둔다**(모드 0600, 추가 전용) |
| 키(환경변수) | `PL_AUTH_SECRET_KEY`, `PL_ACCOUNT_SECRET_KEY`, `PL_AUDIT_ANCHOR_KEY`, 선택 `PL_BACKUP_KEY`. DB 에 없다 |
| 로그 | 표준 출력. 설치 코드는 여기에만 한 번 나온다 |

컨테이너: 이미지는 `/data` 볼륨에 DB 를 둔다(distroless, 셸·curl·`pg_dump` 없음). 앵커 파일은 `/data` 가 아닌 다른 볼륨에 마운트한다. 컨테이너 안에서 `erp-admin` 을 실행하려면 같은 이미지·같은 볼륨·같은 환경변수로 일회용 컨테이너를 띄운다(`/app/erp-admin`).

## 2. 설치

1. **준비**: 바이너리(`make build` → `bin/`) 또는 이미지. 필수 환경변수는 이 문서 부록 10절 표를 본다. 최소 운영 값:
   - `PL_BASE_URL`: 사용자가 접속하는 https 주소(로그인 후 돌아올 주소와 쿠키 보안 설정이 여기서 정해진다).
   - `PL_DB_PATH`(또는 `PL_DB_URL`): 영구 디스크 위의 경로.
   - 키 3종: `openssl rand -base64 32` 로 각각 따로 만든다(`PL_AUTH_SECRET_KEY`, `PL_ACCOUNT_SECRET_KEY`, 앵커용 `PL_AUDIT_ANCHOR_KEY` 는 16바이트 이상의 임의 문자열). **세 키 모두 백업과 따로 안전한 곳에 보관한다.**
   - `PL_AUDIT_ANCHOR_PATH`: DB 와 다른 볼륨의 파일.
   - 메일을 쓰면 SMTP 설정(`PL_SMTP_HOST` 등, 부록 표).
   - `PL_DEV_IDP`·`PL_DEV_SEED_PASSWORD` 는 **운영에서 쓰지 않는다**(9절).
2. **리버스 프록시**: 사용자는 https 로 프록시에 접속하고 프록시가 서버(`PL_ADDR`)로 넘긴다. 상태를 바꾸는 요청은 `Origin` 이 `PL_BASE_URL` 과 같아야 하므로 프록시가 `Origin`·`Host` 를 바꾸지 않게 한다.
3. **첫 기동과 설치 코드 확인**: 빈 DB 로 처음 기동하면 서버 **로그에 설치 코드가 한 번** 출력된다(`docker logs <컨테이너>` 또는 콘솔). 직접 정하려면 `PL_SETUP_CODE`(16자 이상)를 쓰고 이 경우 로그에는 값이 나오지 않는다. 코드는 서버를 운영하는 사람만 볼 수 있다.
4. **설치 마법사**: 브라우저에서 `/setup` 으로 가서 설치 코드를 입력하고 단계를 따른다(회사 정보 → 첫 관리자 → 부서(선택) → 확인). 코드를 5번 연속 틀리면 15분간 잠긴다. 완료하면 마법사는 영원히 닫힌다(그 뒤 `/setup` 은 404).
5. **설치 후 점검**: 관리자로 로그인해 감사 로그 화면의 "변조 여부 검증"이 통과인지, 메일을 쓰면 시험 메일이 가는지 본다. 그 다음 **첫 백업과 복구 리허설**(4·5절)을 한다.

## 3. 업그레이드

무중단이 아니다. 순서:

1. **백업(필수)**: `erp-admin backup`(4절). 성공하고 `verify-backup` 이 통과한 세트가 있는 것을 확인한다.
2. **새 바이너리(이미지)로 교체**.
3. **기동**: 시작할 때 마이그레이션이 자동으로 적용된다. 하나라도 실패하면 기동을 중단한다(반쯤 적용된 상태로 뜨지 않는다). 로그에서 적용된 번호를 확인한다.
4. **확인**: `/healthz`, 로그인, 감사 로그 "변조 여부 검증".
5. **롤백**: 마이그레이션은 앞으로만 간다. 다법인(B44) 이관 뒤에 기록된 감사 레코드(법인 값이 0 이 아닌 것)는 이전 바이너리의 체인 검증에서 변조로 보이므로, 이전 바이너리로 돌아갈 때는 반드시 DB 도 이관 전 백업으로 되돌린다. 이전 바이너리로 돌아가려면 **DB 도 백업으로 되돌려야 한다**: 서버를 멈추고 `erp-admin restore <세트> --replace`(5절). 이전 버전이 만든 백업은 새 버전이 복구할 수 있지만, 새 버전이 만든 백업은 이전 바이너리가 복구를 거부한다("더 새로운 버전에서 만들어졌습니다").

## 4. 백업

```
erp-admin backup                      # 세트 한 개를 만든다. 서버가 켜져 있어도 된다.
erp-admin backup --encrypt            # PL_BACKUP_KEY 로 암호화(외부 저장소로 내보낼 때 권장)
erp-admin backup --keep 30 --label weekly
erp-admin list-backups
erp-admin verify-backup <세트>        # 해시·복호화·DB 점검(무결성·감사 체인·마이그레이션 번호)을 판정표로 본다
```

- **무엇이 만들어지나**: `<PL_BACKUP_DIR>/pl-<UTC 시각>[-라벨]/` 디렉터리 하나(매니페스트, DB 스냅샷, 앵커 사본, SHA256SUMS). 디렉터리 0700, 파일 0600. 백업에는 개인정보와 비밀번호 해시와 봉한 계좌번호가 들어 있으므로 **접근을 통제**한다.
- **일관성**: 쓰는 중에도 한 시점의 일관된 사본을 만든다(단순 파일 복사가 아니다). 만든 스냅샷에서 무결성·외래 키·감사 체인·불변식(전표 차대변, 재고 합계 대 원장 합, 번호 카운터)을 점검한다. **무결성·외래 키·감사 체인이 어긋나면 세트를 만들지 않는다**(손상된 DB 를 정상 백업으로 보관하지 않는다). 업무 불변식(전표 차대변·재고 합계 대 원장·번호 카운터) 위반은 **경고**로 세트에 남기고 백업은 진행한다(출력의 "경고", 매니페스트, 실행 기록 `backup_runs`, 감사 `system.backup` 에 항목·건수). 업무 데이터가 조금 틀어진 회사가 백업을 아예 못 하는 것이 더 위험하기 때문이다. 경고는 사람이 읽고 원인을 점검한다.
- **보존**: 기본 14개(`--keep`, `PL_BACKUP_KEEP`, 최소 2). 새 백업이 검증을 통과한 뒤에만 오래된 세트를 지운다. 실패한 실행은 아무것도 지우지 않는다. 디스크 여유가 직전 백업 크기의 1.5배보다 적으면 시작하지 않는다.
- **암호화**: `PL_BACKUP_KEY`(16자 이상). 키는 백업과 **따로** 보관한다. 키를 잃으면 그 세트는 복구할 수 없다.
- **다른 디스크·원격 복제**: 백업 디렉터리는 DB 와 다른 디스크를 권장한다. 세트 디렉터리를 통째로 복사(rsync·객체 저장소)하면 된다. 복제본도 `verify-backup` 으로 확인한다.
- **스케줄**: 서버 안에 스케줄러는 없다(서버 장애와 백업 중단을 분리). 호스트의 스케줄러를 쓴다:

  ```
  # cron: 매일 03:10
  10 3 * * * /opt/pl/erp-admin backup >> /var/log/pl-backup.log 2>&1
  ```
  ```
  # systemd 타이머: pl-backup.service 가 erp-admin backup 을 실행하고 pl-backup.timer 가 OnCalendar=*-*-* 03:10:00 로 호출한다.
  ```
  ```
  # Kubernetes CronJob: 서버와 같은 이미지·같은 볼륨·같은 환경변수, command: ["/app/erp-admin", "backup"], schedule: "10 3 * * *"
  ```
- **복구 리허설 주기**: 월 1회를 권장한다(5절). 리허설을 하지 않은 백업은 복구된다는 보장이 없다.
- **PostgreSQL**: `erp-admin backup` 이 `pg_dump -Fc` 를 호출한다(`PL_PG_DUMP` 로 경로 지정, 기본은 PATH). 컨테이너 이미지에는 `pg_dump` 가 없으므로 호스트나 사이드카에서 실행한다. 일관된 스냅샷을 내보내 같은 시점의 감사 체인 머리를 매니페스트에 적는다. 시점 복구(WAL 보관)는 DB 운영자의 책임이고 이 도구는 논리 백업만 한다.

## 5. 복구

**복구는 현재 DB 의 변경을 되돌린다.** 시작하기 전에 현재 상태가 필요 없는지, 아니면 먼저 `erp-admin backup` 으로 지금 상태를 보존할지 정한다.

1. **서버와 erp-mcp 를 모두 멈춘다.** 사용 중이면 도구가 거부한다.
2. **리허설로 먼저 확인**(권장): `erp-admin restore <세트> --rehearse`. 임시 위치에 복구해 판정표만 보이고 모두 지운다. 운영 파일은 바뀌지 않는다. 서버 기동까지 확인하려면 `scripts/restore-rehearsal.sh`(최신 세트를 복구해 임시 DB 로 서버를 임의 포트에 띄워 `/healthz` 를 확인하고 정리한다; 결과를 `--record` 로 남긴다).
3. **복구**: 비어 있는 대상이면 `erp-admin restore <세트>`, 기존 DB 가 있으면 `--replace`(기존 DB·WAL·앵커를 `.pre-restore-<UTC>` 로 옆에 보존하고 삭제하지 않는다). 대화형 터미널에서는 데이터베이스 이름을 입력해 확인한다(`--yes` 로 생략).
4. **판정표 읽기**: 항목마다 `통과/경고/실패`. 세트 무결성·해시·마이그레이션 번호·무결성 검사·감사 체인·체인 머리 일치·앵커 대조·불변식·손실 구간·세션 폐기. **하나라도 `실패` 면 확정하지 않고 종료 코드 1**이며 기존 DB 는 그대로다. `경고` 는 사람이 읽고 판단한다(예: "앵커 검증 안 됨", 업무 불변식 위반: 복구는 진행되고 결과 보고에 위반 항목이 적힌다).
5. **손실 구간의 의미**: 백업 이후에 쌓인 감사 기록은 복구로 사라진다. 이전 앵커 파일에 복구 시점보다 큰 번호의 줄이 있으면 그 범위(번호·시각·줄 수)를 판정표와 복구 후 첫 감사 기록(`system.restore`)이 남긴다. 복구는 감사 기록을 몰래 되감는 수단이 되지 못한다. **`.pre-restore-*` 앵커 파일은 증거이므로 지우지 않고 보관한다.**
6. **세션·토큰 후처리**: 복구하면 모든 웹 세션이 폐기되어 다시 로그인한다. 개인 토큰은 기본 유지되고 `--revoke-tokens` 로 전부 폐기할 수 있다. 백업 이후에 폐기·정지된 토큰이나 계정이 되살아났을 수 있으니 **보고서의 안내대로 검토**한다.
7. 복구 뒤 서버를 기동하고(백업이 오래된 버전이면 마이그레이션이 적용된다) 감사 로그 "변조 여부 검증"을 확인한다.
8. PostgreSQL: **비어 있는 새 데이터베이스에만** 복구한다(덮어쓰기 없음). 운영자가 새 데이터베이스를 만들어 `PL_DB_URL` 을 그쪽으로 가리키고 실행한다. `pg_restore` 가 필요하다.

SQLite 세트를 PostgreSQL 로(또는 반대로) 복구하지 않는다. 그것은 이관 도구의 일이다(SQLite→PG 이관: 해당 기능 명세 11절의 `db-migrate`, 서버를 멈춘 뒤 실행하고 이관 전에 백업한다).

## 6. 키 관리

| 키 | 쓰임 | 보관 | 잃으면 |
|---|---|---|---|
| `PL_AUTH_SECRET_KEY` | 2단계 인증(TOTP) 비밀키 암호화 | 서버 비밀 저장소, 백업과 **따로** | 저장된 비밀키를 풀 수 없다: 전원 2단계 재등록(관리자가 사용자별 초기화) |
| `PL_ACCOUNT_SECRET_KEY` | 계좌번호 봉인, 알림 웹훅 주소 봉인 | 같음 | 기존 계좌번호·웹훅 주소를 풀 수 없다: 거래처·자금 계좌 계좌번호 재입력, 웹훅 대상 다시 등록 |
| `PL_AUDIT_ANCHOR_KEY` | 감사 앵커 줄 서명 | 같음 | 기존 앵커 줄의 서명 검증이 모두 실패: 감사자가 확인한 뒤 앵커를 명시적으로 다시 시작(`anchor_lost` 절차, 7절) |
| `PL_BACKUP_KEY` | 백업 암호화(선택) | 백업과 **따로**(같은 곳에 두지 않는다) | 그 키로 암호화한 세트는 복구할 수 없다 |

**교체(회전)**: 두 키(auth, account)는 재등록·재입력 없이 바꿀 수 있다.

```
# 새 키를 만들어 임시 환경변수에 둔다. 옛 키는 지금 서버가 쓰는 값 그대로다.
export NEW_ACCOUNT_KEY=$(openssl rand -base64 32)
erp-admin rotate-key account --new-key-env NEW_ACCOUNT_KEY
erp-admin rotate-key auth --new-key-env NEW_AUTH_KEY      # TOTP
```
- 서버와 erp-mcp 를 먼저 **멈춘다**(사용 중이면 거부). 시작 전에 자동 백업(`pre-rotate-*` 라벨)을 만든다. 실패하면 교체하지 않는다.
- 옛 키로 풀어 새 키로 다시 봉하는 일을 **한 트랜잭션**으로 한다. 하나라도 풀리지 않으면 전체를 되돌린다(옛 키가 틀렸을 때). 끝나면 새 키로 표본을 풀어 보고 옛 키로는 풀리지 않는지 확인한다.
- 끝나면 **서버 환경의 키를 새 값으로 바꿔 기동**한다. 옛 키는 시작 전 백업을 복구할 일을 대비해 그 백업을 지울 때까지 보관한다.
- 계좌 키(`account`) 교체는 계좌번호 열과 알림 웹훅 대상 주소에 더해 **변경 웹훅 구독의 봉인 덩어리(주소·서명 비밀·교체 중인 옛 비밀)도 함께 다시 봉한다.** 교체 뒤 구독을 다시 등록할 필요가 없고 서명 비밀도 그대로다.
- 계좌 키 교체는 **전자세금계산서 대행사 설정의 봉인 덩어리(엔드포인트·API 키·인증서·개인키·비밀번호)도 함께 다시 봉한다**(`tax_asp_settings.secret_sealed`, 용도 `tax-asp`). 교체 뒤 대행사 설정을 다시 입력할 필요가 없다. 모의 대행사는 비밀이 없어 봉인하지 않는다.
- 감사 `system.key_rotated` 에 키 이름과 건수만 남는다.
- 앵커 키(`PL_AUDIT_ANCHOR_KEY`) 교체 도구는 아직 없다(검증기가 키 세대를 알아야 한다). 바꿔야 하면 감사자와 함께 앵커 재시작 절차(7절)로 한다.
- 키가 유출됐다고 의심되면 교체하고, 그 키로 만든 백업 세트와 로그를 정리한다.

## 7. 감사 무결성 점검

- 관리자·감사자 화면 "변조 여부 검증"은 해시 체인과 외부 앵커를 함께 대조한다. 등급: `verified`(체인·앵커 일치), `chain_only`(앵커 꺼짐·비어 있음: 외부 대조 안 됨), `lost_history`(과거에 앵커를 유실한 이력), `failed`(변조 감지).
- 앵커 상태 의미: `ok` 정상 / `empty` 아직 기록 없음 / `file_corrupt` 파일 손상·위조 / `tail_deleted` 마지막 기록 삭제 의심 / `content_recomputed` 내용 재계산 의심 / `anchor_lost` 앵커 줄 유실.
- **`anchor_lost` 대응**: 앵커 파일이 삭제되었거나 끝이 잘렸다. 조용히 새로 시작하지 않는다. 감사자가 원인을 확인한 뒤 앵커를 명시적으로 다시 시작한다(이력은 "앵커 유실 이력 있음"으로 계속 남는다).
- 정기 점검: 주 1회 "변조 여부 검증"을 보고, 월 1회 복구 리허설과 함께 앵커 사본까지 확인한다.

| 증상 | 원인·확인 | 조치 |
|---|---|---|
| 기동 실패: 마이그레이션 | 로그의 마이그레이션 번호·오류 | DB 를 그대로 두고 오류를 수집한다. 직전 백업으로 롤백(3절 5)하거나 개발 팀에 전달 |

| 기동 실패: 앵커 | 앵커 키는 있는데 경로가 없거나 쓸 수 없음 | 경로·권한(0600)·볼륨 마운트 확인 |
| DB 파일 잠김·"사용 중" | 다른 프로세스(서버·erp-mcp·erp-admin)가 DB 를 연 상태 | 모두 멈춘 뒤 다시 실행 |

| 로그인 불가: 설치 코드 분실 | 완료 전에만 필요 | 서버를 다시 기동하면 새 코드가 로그에 나온다(`PL_SETUP_CODE` 로 지정해도 된다) |
| DB 손상(무결성 오류·체인 깨짐) | 백업이 거부되거나 검증 화면이 `failed` | 서버를 멈추고 마지막 검증 통과 세트로 복구(5절). 손상된 DB 파일은 `--replace` 가 옆에 보존한다 |
| 디스크 가득 | 백업이 "여유 공간 부족"으로 시작을 거부 | 오래된 세트 정리, 다른 디스크로 이동. 서버는 DB 쓰기가 실패하면 오류를 낸다 |

| 메일·웹훅 실패 | 알림 발송 기록(관리자 화면)의 실패 사유 | 사유 문장대로 조치(SMTP 설정·웹훅 주소·키). 키를 잃었으면 웹훅 대상을 다시 등록 |
| 느림 | SQLite 는 쓰기 연결이 하나, PG 는 연결 수 상한(`PL_DB_MAX_CONNS`) | 오래 걸리는 내보내기·일괄 작업이 겹치는지 확인. 규모가 크면 PostgreSQL 로 이관 |

## 9. 보안 체크

- 최소 권한 계정으로 서버를 실행한다(컨테이너는 nonroot). DB 파일·앵커 파일·백업 디렉터리는 서버 계정만 읽는다(0600/0700).
- 노출 포트는 리버스 프록시(https)만. 서버 포트(`PL_ADDR`)는 외부에 열지 않는다. PostgreSQL 은 원격이면 `sslmode=require` 이상.
- 로그에는 비밀이 없다(설치 코드는 `PL_SETUP_CODE` 를 쓰면 로그에도 없다). 로그 보존 기간을 정하고, 외부 수집을 한다면 설치 코드가 수집되는 것을 전제로 `PL_SETUP_CODE` 를 쓴다.
- **개발 설정을 운영에서 쓰지 않는다**: `PL_DEV_IDP`(비밀번호 없는 로그인), `PL_DEV_SEED_PASSWORD`(약한 시드 비밀번호). 켜져 있으면 서버가 경고한다.
- 백업 파일은 개인정보·봉한 계좌번호를 담는다: 접근 통제, 외부 보관 시 `--encrypt`, 키는 따로.
- 키·토큰·비밀번호를 명령 인자나 채팅에 붙이지 않는다. `erp-admin rotate-key` 는 환경변수 이름만 받는다.

## 11. 다법인 재고 평가·월 마감·법인 간 이동(B51)

법인이 둘 이상인 설치에서 재고 평가와 월 마감 재고는 **법인마다 따로** 쓰고 읽는다. 법인이 하나뿐인 설치에서는 화면과 응답이 이전과 같고 아래 요소가 나타나지 않는다. 기능 명세는 해당 기능 명세다.

### 법인별 평가

- 같은 품목이라도 법인마다 평균 단가(이동평균)와 재고 금액이 따로 있다. 한 법인의 입고·출고·소급 입력은 다른 법인의 단가를 바꾸지 않는다. 화면의 품목 재고·수불부·월별 재고 현황은 상단의 법인 선택기(현재 법인)를 따르고, 법인 이름이 머리말에 나온다.
- 단가·금액 열은 법인과 별개로 `inventory:valuation_read` 권한(재무·관리자·감사)이 있을 때만 보인다. 내보내기 파일도 같다(금액 포함 파일은 권한이 없으면 받을 수 없다).
- 그룹 범위(전체 법인) 권한이 있으면 법인 선택기에서 "전체 법인"을 고를 수 있다. 이때는 법인마다 단가가 달라 단가를 합산하지 않고 법인별 줄과 소계만 보인다. 마감·해제와 이동은 전체 모드에서 할 수 없다("법인을 하나 골라야 합니다").
- 내보내기·가져오기 대조·MCP 도구의 `entity`(법인 코드)는 권한이 있는 법인 안에서만 고를 수 있다. 모르는 코드는 조건 오류(400), 권한 밖 법인과 `*`(그룹 범위 아님)는 권한 없음(403)이며 감사 로그에 거부로 남는다. MCP 는 두 경우 모두 같은 "찾을 수 없는 법인입니다"로 답한다.

### 기존 데이터 이관(업그레이드 때)

- 마이그레이션 0104·0105 가 평가 줄·이동 전표에 법인 열을 더하고, 서버 기동 때 한 번(멱등) 다법인 품목의 평가를 법인별로 다시 계산한다(감사 `valuation.split`, 이 시스템 동작은 감사 화면에 "평가 법인 분리"로 보인다).
- **법인 하나만 쓰던 설치는 값이 한 글자도 바뀌지 않는다.** 다시 계산되는 것은 B44 이후 같은 품목을 둘 이상의 법인 창고에서 실제로 쓴 경우의 **열린 달** 줄뿐이다. 이미 마감된 달의 평가 줄·월말 스냅샷은 그대로이고, 그 달 금액은 법인을 나누기 전 품목 전체 평균 단가로 계산된 값으로 남는다(월별 재고 현황에 안내 문구가 나온다).
- B44 이후 마감한 달의 스냅샷에 다른 법인 창고 줄이 섞여 있으면 읽을 때 현재 법인 창고 줄만 보이고 "일부 줄을 제외했습니다" 안내가 나온다. 저장된 값은 고치지 않는다(추가 전용).
- 이관이 실패해도 서버는 뜬다. 로그에 실패가 남고 다음 기동 때 다시 시도한다. 이전 바이너리로 돌아가려면 3절 5번처럼 DB 도 이관 전 백업으로 되돌린다.
- 창고의 법인은 만든 뒤 바꿀 수 없다(데이터베이스가 거부한다). 법인을 옮겨야 하면 새 창고를 만들고 법인 간 이동으로 재고를 옮긴다.

### 월 마감은 법인별

- 마감·해제 요청·순서 규칙·마감 전 점검·첫 기록월이 모두 현재 법인의 창고와 기록만 본다. 한 법인의 마감이 다른 법인의 입고·출고·이동·실사를 막지 않는다. 점검 화면 첫 줄에 어느 법인의 기록을 보는지 나온다.
- 월 마감은 법인 하나를 고른 상태에서 한다. 법인마다 따로 마감하고 따로 해제 요청서(MCR)를 올린다. 해제 승인은 그 법인의 달만 연다.

### 법인 간 재고 이동

- 출발 창고와 도착 창고의 법인이 다르면 법인 간 이동이다. 두 법인 **모두**에서 재고 관리(`inventory:manage`) 권한이 있어야 한다(그룹 범위 권한이거나 두 법인에 각각 권한을 받은 겸직자). 한쪽에만 권한이 있으면 도착 창고가 목록에 나오지 않는다.
- 두 법인의 해당 월이 모두 열려 있어야 한다. 한쪽이라도 마감이면 이동할 수 없다.
- 출발 법인의 이동 시점 평균 단가로 금액이 정해지고 그 금액이 이동 줄에 고정된다. 두 법인의 재고 수량·금액 합은 이동 전후 같다. 평균 단가가 없으면 0원으로 이동하고 미리보기에 경고가 나온다.
- **재무 수기 전표가 필요하다.** 법인 간 이동은 회계 전표를 만들지 않는다. 재고 평가와 장부가 어긋나지 않게 두 법인의 재무 담당이 필요하면 각자 법인 간 거래 전표를 따로 입력한다(상계·연결 조정도 자동으로 하지 않는다). 이동 화면의 안내 상자가 같은 내용을 알려 준다.
- 이동 전표는 만든 뒤 고치거나 지울 수 없다. 잘못 옮겼으면 반대 방향으로 이동한다(그 시점의 단가로 기록되므로 금액이 달라질 수 있다). 전표 번호는 출발 법인의 번호 체계이고, 도착 법인 목록에도 같은 번호로 보인다. 상대 법인을 볼 권한이 없는 사람에게는 상대 창고 이름 대신 법인 이름만 보인다.
