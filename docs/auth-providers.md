# 로그인 방식 연결 가이드

ProcureLedger 는 로그인 방식을 네 가지 지원합니다. 어떤 방식이든 "누가 들어올 수 있는가"는 한 곳(계정 판정)이 정합니다. 방식은 신원을 증명할 뿐이고, 계정이 있는지·재직 중인지·잠겼는지는 방식과 무관하게 같은 규칙으로 판정합니다. **외부 로그인은 계정을 만들지 않습니다.** 계정은 입사 발령이 만들고, 외부 로그인은 그 계정의 이메일과 일치할 때 한 번 연결됩니다. 퇴사·입사 전·비활성 계정은 어떤 방식으로도 들어올 수 없습니다.

설정 화면은 관리자 메뉴의 **로그인 설정**(`/admin/auth`, 관리자 전용, 로그인 세션으로만 변경 가능)입니다. 비밀값(클라이언트 비밀, SMTP 비밀번호, 키)은 이 화면에 입력칸이 없고 서버 환경변수로만 설정합니다. 화면은 환경변수가 설정됐는지만 보여 줍니다.

이 문서의 실제 외부 서비스(구글·Microsoft·SAML IdP) 연결 절차는 제품 검증에서 실제 서비스와 연결해 확인하지 않았습니다. 코드는 모의 IdP 와 서명 픽스처로 시험했고, 아래 절차는 각 서비스의 일반적인 설정 항목을 정리한 것입니다. 처음에는 시험 계정으로 "연결 시험"을 통과시킨 뒤 켜세요.

## 1. 개요와 선택 가이드

| 방식 | 언제 | 비고 |
|---|---|---|
| 이메일+비밀번호 | 기본. 외부 신원 체계가 없을 때 | argon2id 해시, 정책, 5회 실패 15분 잠금, 선택 2단계 인증(TOTP) |
| 구글 워크스페이스 | 회사가 구글 워크스페이스를 쓸 때 | 허용 도메인(`hd`)으로 제한, 이메일 검증 필수 |
| Microsoft Entra ID | 회사가 Microsoft 365 를 쓸 때 | 단일 테넌트 고정, (`tid`,`oid`) 로 연결 |
| SAML 2.0 | 사내 SSO(Okta·ADFS·Entra·구글 SAML 앱 등) | SP 시작만, 서명 필수, 재생 방지 |

구글·Microsoft·SAML 로그인에는 로컬 2단계 인증을 요구하지 않습니다. 그 서비스(IdP)의 다단계 인증을 켜세요.

## 2. 공통

- `PL_BASE_URL` 은 사용자가 브라우저로 접속하는 주소입니다. 리디렉션 주소·SAML entityID·재설정 링크가 모두 이 값에서 만들어집니다(요청의 Host 헤더는 쓰지 않습니다). 운영은 반드시 https 로 두세요. https 이면 세션 쿠키에 Secure 가 붙습니다.
- https 를 끝내는 프록시(tailscale serve, 로드 밸런서 등) 뒤에서도 출처 검사는 `PL_BASE_URL` 기준입니다. 단 프록시 뒤에서는 로그인 시도 속도 제한(IP 당 분당 20회)이 프록시 주소 하나로 합산됩니다.
- 방식은 **연결 시험에 성공한 뒤에만** 켤 수 있습니다. 시험은 관리자 본인 계정으로 그 방식 로그인을 새 창에서 해 보는 것이고 세션은 만들어지지 않습니다. 켜져 있는 동안은 설정을 바꿀 수 없습니다(먼저 끄고, 바꾸고, 다시 시험).
- 필요한 환경변수가 없는 방식은 켜져 있어도 로그인 화면에 나오지 않고 설정 화면에 사유가 표시됩니다(서버는 그대로 기동합니다).

## 3. 이메일 로그인 시작

1. 계정이 만들어진 직후에는 비밀번호가 없어 로그인할 수 없습니다. 로그인 설정의 사용자 표에서 관리자가 시작합니다.
   - **설정 링크 보내기**(`PL_SMTP_HOST` 가 설정된 경우): 72시간, 1회용 링크로 본인이 비밀번호를 정합니다.
   - **임시 비밀번호 발급**: 14자 임시 비밀번호가 화면에 **한 번만** 보입니다(24시간 유효, 첫 로그인에서 변경 강제). 관리자는 비밀번호를 직접 정할 수 없고, 자기 자신에게는 발급할 수 없습니다(다른 관리자에게 요청).
2. 첫 로그인은 비밀번호를 바꾸기 전까지 변경 화면만 열립니다.
3. 정책(기본): 10자 이상, 영문 대·소문자·숫자·기호 중 3종류 이상, 이메일 앞부분·이름·흔한 비밀번호 금지, 최근 3개 재사용 금지, 만료 없음. 로그인 설정에서 바꿉니다.
4. 5회 연속 실패하면 15분 잠깁니다. 관리자가 사용자 표의 "잠금 해제"로 풀 수 있습니다.

### SMTP(재설정 링크 메일)

`PL_SMTP_HOST`·`PL_SMTP_PORT`·`PL_SMTP_USER`·`PL_SMTP_PASSWORD`·`PL_SMTP_FROM` 을 설정합니다. 포트 465 는 암묵 TLS, 그 밖은 STARTTLS 필수이며 TLS 가 없는 서버로는 보내지 않습니다(로컬 시험 전용 `PL_SMTP_INSECURE=1` 은 `PL_BASE_URL` 이 로컬일 때만 허용). 설정하지 않으면 "비밀번호를 잊으셨나요" 링크가 없고, 비밀번호는 관리자의 임시 비밀번호로 시작·초기화합니다. 발송 실패는 사용자 응답에 드러내지 않고 감사 로그에 오류로 남습니다.

### 2단계 인증(TOTP)

`PL_AUTH_SECRET_KEY`(32바이트 base64, `openssl rand -base64 32`)를 설정하면 켜집니다. 키가 없으면 기능 전체가 꺼지고 필수 설정이 있어도 요구하지 않습니다. 내 계정 화면에서 인증 앱에 키를 등록하고 6자리 코드로 확인하면 복구 코드 8개가 **한 번만** 보입니다. 로그인 설정에서 **권한별** 필수를 정합니다(기본: 역할·부여 관리 또는 로그인 설정 권한을 가진 사람, 곧 기본 관리자). 역할 이름이 아니라 실효 권한 기준이라 사용자 정의 역할로 그 권한을 받은 사람도 대상입니다. 이전 버전의 "필수 역할" 설정은 첫 읽기에서 자동 이관됩니다(저장 형식 `totpRequiredRoles` → `totpRequiredPerms`). 값이 정확히 `["admin"]`(옛 기본값)이면 새 기본값(역할 관리·로그인 설정 권한)으로 바뀌어 재무 같은 다른 역할이 갑자기 2단계 필수가 되지 않고, 그 밖의 목록은 그 기본 역할들이 가진 위험 권한의 합집합이 됩니다. 필수 대상이 미등록이면 로그인 뒤 등록 화면만 열립니다. 기기를 잃으면 복구 코드를 쓰거나 관리자가 "2단계 초기화"를 합니다.

**`PL_AUTH_SECRET_KEY` 교체**: 바꾸면 저장된 TOTP 비밀키를 풀 수 없게 되어 전원이 재등록해야 합니다(필수 대상은 다음 로그인에서 강제). 순서: 관리자가 필요한 사용자에게 안내 → 키 교체 후 재기동 → 사용자들이 로그인하면서 재등록. 유출이 의심되어 교체할 때는 그 사이 2단계 인증이 필수 대상에 걸리는지 확인하세요.

### 비상 관리자와 비상 로그인

이메일 로그인을 끄더라도 관리자가 잠기지 않게 **비상 관리자**(1~3명, 활성 관리자, 2단계 인증 등록 필수)를 지정합니다. 비상 관리자는 `/login/emergency`(로그인 화면에 링크 없음)에서 비밀번호와 2단계 코드로 들어옵니다. 사용할 때마다 감사 로그에 경고(`비상 로그인 사용`)가 남고 로그인 설정 화면 상단에 알림이 보입니다. 이메일 로그인을 끄려면 시험에 성공한 외부 방식이 켜져 있고, 그 방식으로 연결된 활성 관리자가 있고, 비상 관리자가 2단계 인증 등록을 마쳐야 합니다(하나라도 모자라면 저장이 거부되고 사유가 나옵니다). 외부 방식 끄기·연결 해제도 같은 검사를 받습니다.

## 4. 구글 워크스페이스

1. Google Cloud 콘솔에서 프로젝트를 만들고 OAuth 동의 화면을 **내부**(조직 사용자만)로 설정합니다.
2. 사용자 인증 정보에서 "OAuth 클라이언트 ID"(웹 애플리케이션)를 만들고 **승인된 리디렉션 URI** 에 `PL_BASE_URL/api/auth/callback` 을 넣습니다(로그인 설정 화면에 복사용 값이 있습니다).
3. 서버 환경변수 `PL_AUTH_GOOGLE_CLIENT_ID`, `PL_AUTH_GOOGLE_CLIENT_SECRET` 을 설정하고 재기동합니다.
4. 로그인 설정의 구글 카드에서 **허용 도메인**(예: `corp.example`)을 입력해 저장합니다. 도메인이 비어 있으면 켤 수 없습니다.
5. **연결 시험**을 누르고 관리자 본인의 구글 계정으로 로그인합니다. 성공하면 가린 이메일·도메인이 보입니다. 그 뒤 **켜기**.
- 서버는 ID 토큰의 서명·대상·만료·nonce, `email_verified=true`, `hd` 가 허용 도메인과 같은지, 이메일 도메인도 같은지를 모두 검사합니다. 개인 구글 계정은 `hd` 가 없어 거부됩니다.

## 5. Microsoft Entra ID

1. Entra 관리 센터의 앱 등록에서 새 등록을 만듭니다. 지원되는 계정 유형은 **이 조직 디렉터리의 계정만(단일 테넌트)**.
2. 리디렉션 URI(웹)에 `PL_BASE_URL/api/auth/callback` 을 넣습니다.
3. "인증서 및 비밀"에서 클라이언트 비밀을 만듭니다. **비밀에는 만료일이 있으니** 갱신 일정을 캘린더에 적어 두세요(만료되면 로그인이 실패하며, 이메일 로그인·비상 로그인으로 복구합니다).
4. 엔터프라이즈 애플리케이션 속성에서 **"할당 필요"** 를 켜고 로그인할 사용자·그룹만 할당하는 것을 권장합니다.
5. 환경변수 `PL_AUTH_MS_CLIENT_ID`(애플리케이션 클라이언트 ID), `PL_AUTH_MS_CLIENT_SECRET` 을 설정하고 재기동합니다.
6. 로그인 설정의 Microsoft 카드에 **테넌트 ID**(디렉터리 GUID)를 입력해 저장합니다(`common`·`organizations` 는 쓸 수 없음). 연결 시험 후 켭니다.
- Entra 의 이메일 클레임은 사용자가 바꿀 수 있고 검증 표시가 없어 신뢰하지 않습니다. 그래서 테넌트 일치(`tid`)가 필수이고, 신원은 (`tid`,`oid`)로 묶이며, 이메일은 **처음 연결할 때만** 등록된 이메일과 비교합니다(없으면 `preferred_username`). 연결 뒤에는 이메일이 바뀌어도 (`tid`,`oid`)로만 인식합니다.

## 6. SAML 2.0

우리는 SP(서비스 제공자)이고 **SP 시작 로그인만** 지원합니다(IdP 시작 응답은 거부). 단일 로그아웃(SLO)은 없습니다: 로그아웃하면 이 서비스의 세션만 끝나고 IdP 세션은 남습니다.

1. SP 인증서·키를 만듭니다(RSA). 키 파일은 저장소 밖에 두고 권한을 `0600` 으로 합니다(넓으면 SAML 이 꺼진 채 시작합니다).
   `openssl req -x509 -newkey rsa:2048 -nodes -keyout sp.key -out sp.crt -days 730 -subj "/CN=procure-ledger-sp"`
2. 환경변수 `PL_SAML_SP_CERT_PATH`, `PL_SAML_SP_KEY_PATH` 에 파일 **경로**를 설정하고 재기동합니다(비밀은 파일에만 있고 DB·화면에는 없습니다).
3. 로그인 설정의 SAML 카드에서 **SP 메타데이터를 내려받거나** entityID·ACS URL 을 복사해 IdP 에 등록합니다. 공통 항목:
   - ACS(Assertion Consumer Service) URL: `PL_BASE_URL/api/auth/saml/acs`, 바인딩 HTTP-POST
   - SP entityID(Audience): `PL_BASE_URL/api/auth/saml/metadata`
   - NameID 형식: **emailAddress**, 값은 등록된 사용자의 **이메일**
   - Assertion 또는 Response 에 **서명**(RSA-SHA256 이상). SHA-1 은 거부됩니다.
4. IdP 의 메타데이터 XML 을 카드에 **붙여넣기**로 등록합니다(URL 자동 조회는 하지 않습니다). 저장할 때 entityID, https SSO 주소(HTTP-Redirect), 서명 인증서 1~2개(교체 중 중복 허용), 크기(256KiB), DTD 금지를 검사합니다. 표시 이름(예: "회사 SSO")은 로그인 버튼에 보입니다.
5. 연결 시험 → 켜기.
- 검증(모두 통과해야 하며 하나라도 실패하면 거부): 서명 필수(서명이 검증한 요소만 읽음, Assertion 이 둘 이상이면 거부), 서명 인증서는 등록한 IdP 인증서와 일치, 발급자·Destination·Audience·Recipient·InResponseTo, 시각(오차 ±2분), Assertion ID 재생 방지, NameID 필수.
- **인증서 교체 절차**: IdP 가 인증서를 바꾸기 전에 새 인증서를 포함한 메타데이터(인증서 2개)를 받아 켜진 방식을 끄고 → 메타데이터를 새 것으로 바꿔 저장 → 연결 시험 → 켜기 → IdP 가 새 인증서로 전환 → 나중에 인증서 하나짜리 메타데이터로 다시 정리합니다. 인증서 만료 30일 전부터 설정 화면에 경고가 보이고, 만료되면 SAML 로그인이 실패하므로 비상 로그인으로 복구합니다. SP 인증서 교체는 새 파일 경로로 재기동한 뒤 SP 메타데이터를 IdP 에 다시 등록합니다.

### 알려진 취약점과 보완(GO-2026-6909)

SAML 라이브러리 `github.com/crewjam/saml` v0.6.3 에 알려진 취약점 GO-2026-6909 가 있고 수정 버전이 아직 없습니다(Assertion 검증 중 nil 포인터 패닉, 이름공간을 구분하지 않는 `Subject.NameID` 해석). 이 서비스는 다음으로 보완합니다.

- 라이브러리 호출과 우리 쪽 검사를 패닉 복구로 감싸 패닉을 일반 거부로 바꿉니다(서버가 죽지 않고, 감사 로그에 사유 `saml_parser_panic`).
- NameID 를 라이브러리의 해석값만 믿지 않고 응답 XML 에서 SAML 2.0 이름공간(`urn:oasis:names:tc:SAML:2.0:assertion`)까지 맞춰 직접 읽어 대조합니다. Assertion·Subject·NameID 는 정확히 하나여야 하고, 다른 이름공간의 NameID 가 끼어 있거나 값이 다르면 거부합니다.
- 암호화 Assertion 은 이 직접 읽기를 할 수 없어 거부합니다(지원하지 않음).
- 부정 시험 세트에 Subject 누락·빈 Subject·빈 NameID·다른 이름공간 NameID·중복 NameID 가 들어 있습니다.

**수정 버전이 나오면** `go.mod` 의 `crewjam/saml` 을 올리고(`govulncheck ./...` 로 확인) 부정 시험 세트를 다시 돌리세요. 위 보완은 그대로 두는 것을 권장합니다(심층 방어). 이 취약점이 걱정되면 SAML 방식을 켜지 않고 구글·Microsoft·이메일 로그인만 쓸 수 있습니다.

## 7. 흔한 오류와 해결

| 증상 | 원인·해결 |
|---|---|
| "등록되지 않았거나 사용할 수 없는 계정" | 이메일이 사용자 목록에 없거나, 퇴사·비활성, 또는 이미 다른 외부 계정이 묶인 이메일. 관리자가 사용자 표에서 연결을 해제하면 다시 연결됩니다 |
| 구글 거부(도메인) | `hd` 가 없거나(개인 계정) 허용 도메인과 다름. 설정 화면의 허용 도메인 확인 |
| Microsoft 거부(테넌트) | `tid` 가 설정한 테넌트 ID 와 다름. 앱 등록의 계정 유형과 테넌트 ID 확인 |
| SAML 거부 | 서버 로그에 사유 코드(서명·발급자·Audience 등)가 남습니다. 시계 오차(서버 시각은 설정 화면에 표시), 인증서 만료, NameID 형식, ACS URL 오타를 확인 |
| 메일이 오지 않음 | `PL_SMTP_*` 확인, 서버 로그와 감사 로그의 오류. 임시 비밀번호로 대체 |
| 로그인이 잠김 | 15분 대기 또는 관리자 해제. 관리자 본인이면 다른 관리자 또는 서버 호스트 복구 명령 |

## 8. 비밀값 교체·유출 시 조치

- 클라이언트 비밀(구글·MS): IdP 에서 새 비밀을 만들어 환경변수를 바꾸고 재기동한 뒤 옛 비밀을 폐기합니다. DB 에는 비밀이 없으므로 DB 유출만으로는 새지 않습니다.
- SMTP 비밀번호: 메일 서비스에서 교체하고 환경변수 갱신.
- SP 키: 새 키·인증서를 만들어 경로를 바꾸고 재기동, IdP 에 SP 메타데이터 재등록.
- `PL_AUTH_SECRET_KEY`: 위 "교체" 절차(전원 재등록). TOTP 비밀키는 암호화되어 저장되므로 DB 만 유출되면 키 없이는 풀 수 없지만, 키까지 유출됐다면 전원 재등록이 필요합니다.
- 개인 토큰은 로그인 방식과 무관하게 유지됩니다. 유출이 의심되는 사용자는 토큰도 폐기하세요.

## 9. 비상 복구(`auth-unlock`)

모든 관리자가 로그인하지 못할 때(잠금, 외부 방식·메타데이터 오류로 이메일 로그인을 끈 상태 등) 서버 호스트에서 실행합니다. DB 파일에 접근할 수 있는 사람만 할 수 있습니다.

```
PL_DB_PATH=<DB 경로> ./bin/erp-admin auth-unlock <관리자 이메일>
```

기존 `./bin/server auth-unlock <관리자 이메일>` 도 같은 구현을 부르는 별칭으로 그대로 동작합니다(컨테이너 이미지에는 `/app/erp-admin` 이 들어 있습니다).

그 계정의 잠금을 풀고, 이메일 로그인이 꺼져 있었다면 다시 켭니다. 감사 로그에 경로 "서버 명령"(cli)으로 남습니다(0053 마이그레이션 이전 기록은 경로 "웹" + `해제한 주체`=cli).

## 10. 계정 자동 동기화(SCIM 2.0): Entra ID·Okta·구글

IdP 에서 입사·퇴사·부서·직위 변경을 ERP 로 자동으로 받습니다. 받은 변경은 관리자가 화면에서 하는 인사 발령과 같은 경로(같은 검증·이력·감사)로 반영되고, **효력일은 받은 날(오늘)** 입니다. 과거 날짜를 보내도 받지 않습니다. 위험 권한이 있는 계정(역할·로그인 설정·지급 등 관리 권한 보유자)은 동기화로 조회도 수정도 되지 않고, 동기화로 위험 권한이 새로 생기는 발령은 거부됩니다. 로그인은 이 문서의 4~6절 방식(구글·Microsoft·SAML)으로 하며, 동기화로 만든 계정에는 비밀번호가 없습니다.

설정 화면은 관리자 메뉴의 **계정 동기화**(`/admin/scim`)입니다(조회는 감사도 가능, 변경은 관리자만, 로그인 세션으로만). 이 절의 외부 서비스 설정 절차도 실제 서비스와 연결해 확인하지 않았고, 코드는 모의 IdP(Entra 형·Okta 형·규격형)로 시험했습니다. 처음에는 시험 사용자 한두 명으로 확인한 뒤 전체로 넓히세요.

### 10.1 ERP 쪽 준비(공통)

1. **동기화 설정**: "동기화 설정"에서 *기본 조직 코드*(부서 정보가 없는 입사의 소속)와 *기본 직위*(직위가 없는 입사)를 정하고 "계정 동기화 사용"을 켭니다. 기본값이 없으면 부서·직위 없는 입사는 거부됩니다. 기본 역할은 `staff` 이며 위험 권한이 든 역할은 저장되지 않습니다.
2. **연동 토큰 발급**: "연동 토큰"에서 이름·IdP·범위(사용자만 또는 사용자와 그룹)·유효 기간을 정해 발급합니다. 토큰(`pls_…`)은 **발급 직후 한 번만** 보이니 바로 IdP 의 비밀 토큰 칸에 붙여 넣으세요. 같은 IdP 의 유효 토큰은 2개까지라서 교체할 때는 새 토큰을 발급해 IdP 에 넣고 확인한 뒤 옛 토큰을 폐기합니다. 만료 14일 전부터 화면과 도입 점검표가 알려 줍니다.
3. **연결 주소**: 화면에 보이는 `https://<서버 주소>/scim/v2` 가 IdP 의 *테넌트 URL(기본 URL)* 입니다. 운영은 https 만 쓰세요. 서버가 프록시 뒤에 있으면 `PL_BASE_URL` 이 바깥 주소와 같아야 하고, IdP 의 출발지 주소가 고정이면 `PL_SCIM_ALLOW_CIDR` 로 허용 출발지를 좁힐 수 있습니다(프록시 뒤에서는 프록시 주소가 보입니다).
4. **그룹 연동(선택)**: 그룹을 쓰려면 토큰 범위를 "사용자와 그룹"으로 하고 설정의 *그룹 연동*에서 하나를 고릅니다. **조직**: 그룹 멤버가 그 조직으로 전보됩니다(이때 사용자의 부서 속성은 무시하고 그룹 소속이 정합니다). **역할**: 그룹 멤버에게 역할이 부여됩니다(위험 권한이 든 역할은 고를 수 없습니다). 그 뒤 "그룹 매핑"에서 IdP 그룹을 조직 또는 역할에 연결합니다. 매핑이 없는 그룹은 거부되고 "매핑이 없는 그룹"에 나타납니다. 연동 방식을 바꾸려면 다른 방식의 매핑을 먼저 지워야 합니다.

받는 속성: `userName`(이메일, 로그인 식별자, 바꿀 수 없음), `externalId`(없으면 이메일로 대신), `displayName`(또는 `name`), `active`, `title`(→ 직위 이름, 직위 표와 같아야 함), 엔터프라이즈 `department`(→ 조직 코드 또는 이름), `employeeNumber`(생성 때만), `phoneNumbers`(work). `roles`·`password`·`manager` 는 받지 않습니다. 없는 부서·직위는 거부되며(조직을 자동으로 만들지 않습니다) 같은 요청의 다른 변경도 함께 취소됩니다. 퇴사는 마지막 근무일 다음 날이 아니라 **받은 날부터** 효력이 있고, 입사한 날에는 퇴사 처리를 할 수 없습니다(다음 날 다시 전송되거나 인사 발령 화면에서 처리).

### 10.2 Microsoft Entra ID

1. Entra 관리 센터 > **엔터프라이즈 애플리케이션** > 새 애플리케이션 > *직접 애플리케이션 만들기*(갤러리에 없는 앱)로 앱을 만들고, **프로비전** > 시작하기 > 프로비전 모드 **자동**.
2. **관리자 자격 증명**: *테넌트 URL* 에 `https://<서버 주소>/scim/v2`, *비밀 토큰* 에 발급한 `pls_…` 를 넣고 **연결 테스트**.
3. **매핑 > 사용자 프로비전**에서 특성을 맞춥니다.
   | Entra | SCIM | 비고 |
   |---|---|---|
   | `userPrincipalName`(또는 `mail`) | `userName` | 일치 특성으로 쓰지 않습니다 |
   | `objectId` | `externalId` | 일치 특성(우선순위 1) |
   | `displayName` | `displayName` | |
   | `jobTitle` | `title` | 직위 표의 이름과 같아야 합니다 |
   | `department` | `urn:ietf:params:scim:schemas:extension:enterprise:2.0:User:department` | 조직 코드 또는 이름. 그룹 조직 모드면 보내지 않아도 됩니다 |
   | `telephoneNumber` | `phoneNumbers[type eq "work"].value` | |
   | `Switch([IsSoftDeleted], , "False", "True", "True", "False")` | `active` | 기본값 그대로 |
   Entra 가 `active` 를 문자열 `"True"`/`"False"` 로 보내도 받습니다.
4. **범위**는 "할당된 사용자 및 그룹만 동기화"를 권장합니다. 그룹 연동을 쓰면 **매핑 > 그룹 프로비전**을 켜고 `displayName`→`displayName`, `objectId`→`externalId`, `members`→`members` 로 맞춘 뒤 ERP 의 그룹 매핑에 그룹의 `objectId` 를 그룹 식별자로 넣습니다.
5. 시험: **주문형 프로비전**으로 한 사용자를 보내 ERP 의 동기화 기록과 인사 발령 이력을 확인하고, 문제가 없으면 프로비전 상태를 **켜기** 로 합니다. 첫 주기 뒤에는 보통 약 40분마다 변경분을 보냅니다.

### 10.3 Okta

1. Okta 관리 콘솔 > Applications > *Create App Integration*(SAML 로그인 앱) 또는 SCIM 을 지원하는 사용자 지정 앱 통합을 만들고, 앱의 **Provisioning** 탭에서 **SCIM** 연동을 켭니다(Okta 가 *SCIM 2.0 Test App* 같은 범용 앱을 제공하면 그것을 써도 됩니다).
2. **SCIM connector base URL** 에 `https://<서버 주소>/scim/v2`, **Unique identifier field for users** 에 `userName`, **Supported provisioning actions** 에 *Push New Users*·*Push Profile Updates*(·*Push Groups*), **Authentication Mode** 는 *HTTP Header* 로 두고 토큰에 발급한 `pls_…` 를 넣습니다. **Test Connector Configuration** 으로 확인합니다.
3. **To App** 설정에서 *Create Users*·*Update User Attributes*·*Deactivate Users* 를 켭니다. 속성 매핑에 `title`·`department`(엔터프라이즈 확장)를 추가하세요. Okta 는 `externalId` 를 보내지 않는 경우가 있어 이때는 이메일이 식별자가 됩니다.
4. 사용자 비활성화는 `active=false` 로 오며 ERP 에서 퇴사 발령이 됩니다. 앱에서 사용자를 지우는 `DELETE` 도 같은 퇴사 처리입니다(행은 지우지 않습니다).
5. 그룹은 **Push Groups** 에서 Okta 그룹을 보내고, ERP 그룹 매핑의 그룹 식별자에는 Okta 그룹 ID 를 넣습니다.

### 10.4 구글 워크스페이스

**결론(2026-11 확인): 구글은 사용자 지정(비갤러리) 앱으로의 SCIM 푸시를 "사용자 지정 SCIM 프로필(베타)"로만 제공하며 제한된 참가자에게만 열려 있습니다.** 관리 콘솔의 해당 SAML 앱 상세 화면에 **자동 프로비저닝(Autoprovisioning)** 항목이 보이는 조직만 쓸 수 있고, 보이지 않으면 아직 사용할 수 없습니다(출처: [Google Workspace 관리자 도움말: 맞춤 SCIM 프로필로 자동 사용자 프로비저닝(베타)](https://knowledge.workspace.google.com/admin/users/advanced/automated-user-provisioning-with-custom-scim-profiles)). 그 문서의 요건은 SCIM 2.0 서버(POST·GET·PATCH, PUT 대체, DELETE), 전달자(Bearer) 토큰 인증(OAuth 토큰은 미지원), 슈퍼 관리자 권한이며 ProcureLedger 의 SCIM 서버가 모두 해당합니다. 베타의 제공 범위는 구글이 바꿀 수 있으니 설정 전에 위 문서를 다시 확인하세요.

**항목이 보이는 경우**: 구글 관리 콘솔 > 앱 > 웹 및 모바일 앱에서 ProcureLedger 를 SAML 앱으로 먼저 등록하고(6절), 앱 상세 화면의 **자동 프로비저닝**에서 *액세스 토큰* 에 발급한 `pls_…`, *엔드포인트 URL* 에 `https://<서버 주소>/scim/v2` 를 넣은 뒤 특성 매핑(이메일→`userName`, 이름→`displayName`, 부서→엔터프라이즈 `department`, 직함→`title`)을 맞추고 **테스트**를 한 다음 상태를 **활성**으로 바꿉니다(마침을 눌러도 켜지지 않습니다).
- 구글의 테스트는 임시 계정을 만들고 수정한 뒤 지웁니다. ProcureLedger 는 입사한 날에는 퇴사 처리를 받지 않으므로(409) 삭제 단계가 거부되고 임시 계정이 재직 상태로 남을 수 있습니다. 시험 뒤 인사 발령 화면에서 그 계정을 퇴사 처리하세요.
- *비활성화 동작*(앱 해제·정지·삭제 때 정지/삭제와 지연 시간)은 보수적으로(지연을 길게) 정하세요. 삭제는 퇴사 발령이 되며 되돌리려면 재입사 발령이 필요합니다.
- 구글은 그룹 멤버십을 "할당된 그룹의 멤버만 프로비저닝"으로 다루며 그룹 객체 자체를 SCIM Groups 로 보내지 않습니다. 그룹 연동(10.1)은 쓰지 않는 것을 권장합니다.

**항목이 보이지 않는 경우(대체 절차)**: 구글에서는 SCIM 을 쓸 수 없으므로 (1) 로그인은 구글 로그인(4절)·SAML(6절)로 두고, (2) 사용자 변경은 조직 CSV 반영(조직 관리 > 가져오기)으로 합니다. 구글 디렉터리 사용자 목록을 CSV 로 내려받아 양식에 맞춰 올리면 입사·퇴사·전보가 같은 발령 경로로 반영됩니다. 자동화가 꼭 필요하면 Entra·Okta 같은 별도 IdP 를 구글과 연결해 그쪽에서 이 10.2·10.3 절차로 보냅니다.

### 10.5 확인과 문제 해결

| 증상 | 원인·해결 |
|---|---|
| 연결 테스트가 401 | 토큰 오타·폐기·만료. 토큰은 발급 때 한 번만 보이므로 잃었다면 새로 발급합니다. 인증 실패가 분당 20회를 넘으면 그 출발지가 잠깐 막힙니다(429) |
| 403 "동기화가 꺼져 있습니다" | 화면의 "계정 동기화 사용"이 꺼져 있음. 그룹 요청은 토큰 범위가 "사용자와 그룹"이어야 합니다 |
| 403 "허용되지 않은 출발지" | `PL_SCIM_ALLOW_CIDR` 에 IdP 의 주소가 없음 |
| 400 "부서 정보가 없습니다" | 요청에 부서가 없고 기본 조직도 없음. 설정에서 기본 조직 코드를 정하세요 |

| 409 "입사 당일에는 퇴사 발령을 낼 수 없습니다" | 다음 날 다시 전송되거나 인사 발령 화면에서 처리 |
